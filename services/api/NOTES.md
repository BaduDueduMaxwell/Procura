# Buyer intake rationale

Procura now treats buyer intake as a persisted aggregate separate from the existing supplier-decision conversation so text and spreadsheet rows can be corrected without changing proven quotation logic. LangGraph fixes validation order and owns buyer-interrupt/resume state; LangChain supplies typed tools and the optional Gemini structured-output adapter, while pure Python validators remain the authority for repeatable checks. The hosted interpreter now returns procurement intent inside its typed semantic result instead of being blocked by a fixed term list; the local provider accepts unseen catalogue names only when clinical structure is present. SQLAlchemy stores the user-facing aggregate with tenant checks, idempotency keys, and optimistic versions, and the graph checkpointer stores execution position so refreshes and process restarts do not erase progress. Intake HTTP handlers now live in `app/api/intakes.py`; parsing, interpretation, validation, orchestration, persistence, observability, and review creation remain separate concerns.

The likely first failure point is very large or unusually formatted workbooks: this version bounds archive expansion, file size, worksheets, and row count, but does not implement every legacy Excel encoding or merged-header convention. The no-key interpreter cannot understand every possible sentence semantically, so it requires clinical structure or catalogue evidence and fails closed when neither exists; hosted Gemini performs the semantic intent decision. Gate tests cover API ownership, parsing, correction, suggestion decisions, concurrency, refresh/resume, idempotent submission, varied out-of-scope input, unseen medicine names, and critical-review creation. The final local run passed Ruff, the configured mypy gate across 27 backend modules, 88 backend tests, and 29 frontend tests; both deterministic evaluation lanes passed at 100%. Roll back with `git revert <buyer-intake-commit>` and redeploy both services; the additive `procurement_intakes` table can remain unused without affecting earlier code.

The Ghana brand update replaces three unsupported hard-coded aliases with a versioned catalogue of 10 active Ghana FDA product records across multiple manufacturers. Exact brand lookup is deterministic; the buyer sees the registered active ingredient, variant, manufacturer, expiry-backed source record, and must accept or reject before the generic name changes. This approach avoids a live registry dependency and prevents the model from inventing brand relationships, while preserving the original request and decision actor for audit. The likely first failure point is source freshness after a registration expires or a new brand appears, so expired records stop matching and the curated file must be refreshed from the official register. Final verification passed 96 backend tests, 30 frontend tests, 15/15 supplier-decision evaluations, 25/25 buyer-intake evaluations, lint, type checks, the Next.js production build, both container builds, and mobile browser QA at 375×812. Roll back with `git revert <ghana-brand-commit>` and redeploy the API and web services; no database migration is involved.

The downloadable intake template intentionally omits buyer notes so every column contributes directly to validation. It now includes the required quantity units column, preventing a fresh template from producing a missing-unit blocker on every row. A gate test and deterministic evaluation assert the exact focused header. The first likely break is a future required-field change that is not reflected in the template contract. Roll back by reverting the template commit; no service data or schema changes are involved.

The production CI run exposed an overly broad `dict[str, object]` used to assemble typed catalogue suggestions. The validator now constructs sourced and spelling suggestions through explicit Pydantic arguments, preserving runtime behavior while making the two evidence contracts visible to mypy. This was chosen over a cast because a cast would hide future field mismatches rather than prevent them. The likely failure point remains a model-field addition that is updated in only one constructor path. Exact CI mypy, Ruff, the 23 intake tests, and 26 intake evaluations pass after the correction.

The duplicate-resolution update closes the buyer feedback loop by replacing an advisory warning with explicit, recoverable actions: remove the row, keep both rows, or restore a removed row before submission. The service preserves the full removed row, original row count, actor, timestamp, and idempotent action result so the audit trail stays accurate without destructive deletion. Exact duplicate detection now includes quantity and the complete procurement variant, avoiding false positives when a buyer intentionally requests the same medicine in different amounts. Operations was narrowed to the measures that explain intake performance: submitted lists, correction and critical-review volume, first-pass readiness, time to first feedback, time to valid submission, processed rows, buyer corrections, and failed-safe runs. The most likely first failure point is a future change to the duplicate fingerprint that is not applied consistently to both validation and group confirmation; the shared `duplicate_fingerprint` function and regression tests constrain that path. Final verification passed 99 backend tests, 31 frontend tests, 15/15 supplier-decision evaluations, 28/28 buyer-intake evaluations, lint, type checks, both production builds, Docker Compose validation, and buyer and Operations browser QA; rollback is `git revert <duplicate-resolution-commit>` followed by redeploying API and web, with no database migration required.

Catalogue variant correction now gives the buyer a repository-backed option with exact changes, supplier coverage, destinations, currencies, capacity, lead time, price range, and cold-chain evidence before the manual editor. Selection is server-validated against current database records, records the actor and timestamp, and changes only medicine identity fields so quantity and delivery requirements cannot be overwritten accidentally. This was chosen over model-generated correction because catalogue identity and commercial coverage must remain reproducible and inspectable. Unknown medicines receive no fabricated option, and stale or client-invented source identifiers are rejected. The likely first failure point is catalogue freshness when an approved quotation changes between display and selection; the endpoint resolves the option again and returns a refresh message instead of applying stale evidence. Final verification passed 102 backend tests, 32 frontend tests, 15/15 supplier-decision evaluations, 31/31 buyer-intake evaluations, lint, mypy, both production builds, Docker Compose validation, browser console checks, and responsive QA at 375×812, 768×1024, and 1440×900; rollback is `git revert <catalogue-variant-commit>` followed by redeploying API and web, with no database migration required.
